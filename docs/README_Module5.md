# Модуль 5. Сжатие и скорость работы

Скрипт: `scripts/m5_compress.py`, результат — `artifacts/tables/compression.{csv,md}`.

```bash
python scripts/m2_m3_train.py --config configs/pinn_small.json   # компактная PINN
python scripts/m5_compress.py --model pinn
```

## Выводы
* **Явный якобиан** вместо autograd: производные без построения графа; после замены `einsum` по батчу на
  «склейку» касательных в одно матричное умножение — в 1.5 раза быстрее исходной версии и быстрее autograd;
  экспортируется в ONNX/TorchScript (autograd — нет).
* **TorchScript freeze + optimize_for_inference** — ×2.6 по значениям, ×1.5 по производным без потери точности.
* **ONNX Runtime** — ×3.5 по значениям; файл модели не требует PyTorch.
* **fp16-хранение** уменьшает файл вдвое при почти той же точности, но **ломает физику**: шум округления весов
  возвращает нарушения устойчивости (0.017 % → 0.55 %). Для PINN это важное наблюдение — после квантизации
  физику нужно перепроверять (`check_physics`).
* **int8** для такой сети неприемлема: ошибка 11 %, т.к. ln P — гладкая функция с перепадом в 28 единиц,
  и шаг квантизации даёт большие относительные ошибки P.
* **Компактная PINN** (≈ 15 тыс. параметров, 0.06 МБ) обучена с теми же физическими потерями:
  в 4.8 раза меньше и в 4.5 раза быстрее основной по производным, по скорости P,E в ONNX — на уровне таблицы,
  которая весит в 70 раз больше; точность 1.0 % / 1.4 % и 0.05 % нарушений устойчивости.
  Это вариант для гидрокода, где важнее скорость; основная PINN — где важнее точность.


Замер на 10⁸ запросов (батчи по 10⁶): PINN (ONNX) — 184 с, компактная PINN (ONNX) — 65 с, таблица — 45 с.
PINN-T имеет ту же архитектуру, что и PINN-A, поэтому её размер и скорость совпадают.
